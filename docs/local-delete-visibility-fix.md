# 本地删除后的云端目录可见性修复

日期：2026-11-12。已部署修复，原配置和六任务运行状态恢复。

## 原因

旧的真实网盘后端在同步删除时，只把文件按 ID 改名为同一父目录下的 `_twodrive-deleted-<操作标识>`。115Drive 自己的清单过滤这些内部名称，但 115 官方客户端仍会显示图片和缩略图。因此，原名称虽然消失、同步基线也已经移除，用户看到的云端目录却没有清空。

原本本地模拟后端直接删除生成文件；真实云端验收又只检查原名消失和旧正文保留，缺少对原始云端目录可见内容的检查。这次补充“未过滤的原始目录中没有原名或内部图片副本”的验收条件。

## 修复行为

同账号使用独立的 `115Drive 同步历史-<随机标识>` 云端根目录。原事务记录保留，额外保存来源路径、账号与目录身份、原文件 ID/SHA-1、归档位置和操作阶段。文件从同步目录移出，旧正文和恢复映射保留，不清空网盘回收站。

新操作先保留并验证原版本，再按 ID 移入历史区；结果未知时先核对来源和目的位置，避免盲目重复移动。已有删除记录只在新鲜身份、内容及原始目录清单证明归档存在后迁移，不凭旧日志修改同名新文件。历史区禁止重新设为同步任务，避免已删除内容被再次导入。

配置、任务 ID、保留策略、同步根和同步基线不重置。仅联机读取使用明确的只读后端，不触发归档维护。

## 验收范围

专项测试覆盖原始目录可见性、双向删除、旧事务迁移、历史正文核验、重复恢复、丢失移动响应以及另一客户端重建原路径。目录的空性以未过滤的实际子项判断，避免把排除文件或并发新增文件当成不存在。

本地现场与隔离验收证据位于 `runtime/local-delete-fix-20261112/`。云端接口不提供本次已经验证的原子版本条件修改；遇到并发变化时保留内容和记录并报告冲突，不能将这些测试解释为服务端原子事务保证。

397 项完整回归和 57 项重点联合回归通过。独立代码复核确认账号变化、只读写入隔离、目录实际子项、归档版本变化和重启冲突处理。最初完整测试缺少候选默认配置的两项环境错误记录保留；生成无凭据的隔离默认配置后全部通过。

真实云端主验收 8 项通过，327.516 秒，包括真实 CfAPI 双向删除、未过滤的原目录清单、历史正文实际下载、两次重启仅一次移动、提交成功后丢响应恢复以及并发重建保护。随后用最终冻结代码构造陈旧 v1 基线补验，106.86 秒：首轮、冷却期下一轮及新后端均持续报告冲突，移动次数和基线写入均为 0，原 SQLite 项目保留。此补验不声称 115 实际支持原地修改同一文件 ID。三个人工生成的云端根均已清理，原生测试同步根均已注销。

用户指定的真实旧归档已按唯一操作 ID 精确迁移。独立云端读回确认原目录子项为 0，原文件 ID、大小和 SHA-1 在独立历史区相同，原 v1 日志字节未变。迁移前六任务排空，并备份 123 个配置/状态/历史元数据文件；部署未重置同步数据库。

主要证据：`acceptance.json`、`reported-file-repair.json`、`maintenance-control.json`、`source/runtime/delete-visibility-full-suite-final.log`，以及 `source/tests/runs/delete-visibility-*/result.json`。正式修复版本为 `0.3.0-rc4`，发行核验记录另存于同一验收目录。

## 保留边界

历史区保留正文，因此同步删除不是永久清除云端空间。大量旧归档的自动迁移每轮最多处理 4 项，期间可能显示等待恢复；显式迁移支持批处理，完成后不重复扫描旧日志或改写已完成记录。目录移动后若出现并发新增，正文及冲突映射会保留并阻止成功确认，不保证自动把目录移回原位。本次核验以真实云端原始清单为准，没有操作官方客户端界面或进行整机物理断电。
